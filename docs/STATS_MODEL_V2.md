# Модель статистики и штабной отчётности (v2)

Статус: **утверждено владельцем продукта 19.08.2026; уточнено 21.08.2026**.

Статус реализации: **фазы 0–6 и унификация новых обходов выполнены**. Модель
данных, правила цепочки, общий statistics service/API, PPTX, интеграция районной
сводки Excel, пяти-вкладочный frontend и contract-миграция поставляются вместе.
Legacy-колонка `checklist_items.category` и enum-value `overdue` намеренно пока
сохранены для совместимости; новые writers используют category FK, а просрочка
вычисляется. Их физическое удаление возможно только после отдельного аудита
production-интеграций и не является незавершённой частью v2.

Новые обходы не создают и не изменяют ответы чек-листа: единственная рабочая
единица нарушения — `issues` с обязательной активной категорией. Исторические
чек-листовые обходы и их фотографии не удаляются и открываются только для
просмотра. Для периода «За всё время» начальная дата проекта — **01.06.2026
(МСК)**; пользовательский диапазон дат всегда имеет приоритет над быстрым
переключателем периода.

Документ — единый источник правды для переработки статистики, дашборда и
штабных отчётов. Решения ниже сверены с текущими моделями, эндпоинтами и
permissions. При расхождении старого кода и этого документа целевым считается
этот документ; совместимость и переходные правила оговорены явно.

## 1. Цель и границы

Нужна единая модель воронки нарушений и охвата, из которой получают данные:

- новый дашборд приложения с пятью вкладками (§ 8);
- legacy `/reports/weekly` и `/reports/monthly`, которые исправляются, но не удаляются;
- существующий `/reports/export.xlsx`;
- новый штабной PPTX (§ 7).

Корень регулярных расхождений — независимые определения одной метрики. Например,
текущий `admin_dashboard` относит завершённый обход к периоду по `created_at`, а
не по `completed_at`; Excel повторяет часть агрегатов отдельным SQL.

**Архитектурное решение:** новый stats-сервис становится единственным местом
определения сводных метрик. В первой поставке Excel не переделывается визуально,
но его районная сводка должна перейти на тот же сервис не позднее фазы 4. Иначе
заявленная цель единого источника правды не достигается.

## 2. Терминология и воронка нарушений

### 2.1 Когорта замечаний

Все показатели воронки считаются по замечаниям (`issues`), **созданным в отчётном
периоде**, с их **текущим статусом на момент формирования отчёта**:

```text
ВЫЯВЛЕНО (found): issues.created_at входит в период
├── УСТРАНЕНО (closed): status == closed
└── НЕ УСТРАНЕНО (not_fixed): found - closed
    ├── Не приступали (open): status == open
    ├── В работе (in_work): status in {assigned, in_work}
    ├── На проверке (on_check): status in {fixed, control}
    └── На доработке (revision): status == revision_needed

ПРОСРОЧЕНО (overdue) — пересечение, а не слагаемое воронки:
status in {open, assigned, in_work, revision_needed}
AND due_date < сегодня (МСК)
```

Инварианты:

- `not_fixed = found - closed`;
- `not_fixed = open + in_work + on_check + revision`;
- `overdue <= open + in_work + revision`;
- каждый issue когорты входит ровно в одну основную статусную корзину;
- `overdue` не прибавляется к сумме корзин.

Это **когортный снимок**, а не историческое состояние «на конец периода»:
повторное формирование старого отчёта может дать другое распределение статусов.
Дата формирования (`as_of`) обязательно возвращается API и печатается в экспортах.
Если позднее понадобится воспроизводимый исторический снимок, потребуется журнал
переходов со snapshot/as-of запросом; текущий `IssueStatusHistory` не содержит
полную исходную историю для всех старых записей и не заменяет snapshot автоматически.

### 2.2 Закрытия как события

В `/stats/dynamics` «устранено за день» — число переходов
`IssueStatusHistory.new_status == closed` в этот день, независимо от даты создания
issue. Это поток событий, а не `issues_closed` когортной воронки. Поля должны иметь
разные имена в коде (`issues_closed_current` и `closure_events`), чтобы их нельзя
было случайно смешать.

Повторное закрытие после возврата считается новым событием динамики. Когортная
воронка всё равно считает такой issue один раз по его текущему статусу.

### 2.3 Проценты и период

- Проценты — целые, округление `ROUND_HALF_UP`:
  `floor(numerator * 100 / denominator + 0.5)` для неотрицательных значений.
- Деление на ноль даёт `0`.
- Период — МСК-дни, полуоткрытый UTC-интервал
  `[date_from 00:00 MSK, date_to + 1 day 00:00 MSK)`.
- Использовать `app.services.timezone.msk_day_bounds_utc`.
- Общий дефолт дашборда: текущая неделя, понедельник — сегодня (МСК).
- Дефолт штаба: прошлая полная неделя, понедельник — воскресенье (МСК).
- Быстрые периоды дашборда: текущий день, неделя с понедельника, месяц с 1-го
  числа и всё время с 01.06.2026; произвольные даты независимы от них.
- Строка «ИТОГО» в экранной, Excel- и PPTX-сводке рассчитывается по суммарным
  числителям и знаменателям округа. Проценты не усредняются по районам.

Проценты вычисляются в Python общей функцией, не через разные SQL/JS-формулы.

## 3. Модель данных и миграция Alembic

### 3.1 `issue_categories`

```sql
CREATE TABLE issue_categories (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    name VARCHAR(200) NOT NULL UNIQUE,
    sort_order INTEGER NOT NULL DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Используется `uuid_generate_v4()`: проект уже включает `uuid-ossp` и применяет
этот default в bootstrap-схеме.

Seed:

| sort_order | name |
|---:|---|
| 10 | Оборудование |
| 20 | Покрытие |
| 30 | Ограждения |
| 40 | МАФ |
| 50 | Санитарное состояние |
| 60 | Безопасность |
| 70 | Документация |
| 80 | Освещение |
| 999 | Прочее |

### 3.2 Новые поля

```text
checklist_items.category_id UUID NULL REFERENCES issue_categories(id)
issues.category_id          UUID NULL REFERENCES issue_categories(id)
issues.executor_name        VARCHAR(300) NULL
```

Для обоих FK создать индексы. Старая `checklist_items.category VARCHAR(200)`
остаётся на переходный период. Она не может сразу стать «не читаемой и не
записываемой»: текущие admin/checklist, inspection и PDF-экраны используют её.

Переход:

1. Фаза 1 добавляет поля и backfill, старое поле продолжает работать.
2. Фазы 2–5 переводят ORM, API, формы, inspection/PDF/Excel на `category_id` и
   возвращаемое `category_name`.
3. Запись временно dual-write либо централизованно синхронизирует legacy name.
4. Удаление `category` — отдельная миграция после проверки, не часть v2 rollout.

### 3.3 Backfill категорий

В одной ревизии Alembic:

1. Вставить seed через `ON CONFLICT (name) DO NOTHING`.
2. Сначала сопоставить точные нормализованные названия (`lower(trim(...))`).
3. Для остальных классифицировать по `coalesce(category, '') || ' ' || question`.
4. Приоритет ключей:
   - `санитар`, `мусор`, `уборк`, `чистот` → Санитарное состояние;
   - `покрытие` → Покрытие;
   - `оборудован`, `качел`, `горк`, `турник`, `карусел`, `тренаж`, `песочниц` → Оборудование;
   - `огражден` → Ограждения;
   - `маф`, `скамей`, `урн` → МАФ;
   - `безопасн` → Безопасность;
   - `документ`, `табличк`, `паспорт`, `вывеск` → Документация;
   - `освещен`, `свет` → Освещение;
   - иначе → Прочее.
5. `issues.category_id`: сначала категория связанного checklist item; для ручного
   issue — классификация `title || description`; иначе Прочее.

Санитарные ключи идут первыми намеренно, чтобы уборка мусора не терялась в общей
категории оборудования/МАФ. Backfill выполняется raw SQL и сопровождается
проверками: нет `NULL category_id`, сумма строк до/после совпала, распределение
по категориям выведено в миграционный smoke-лог/ручной запрос.

### 3.4 Совместимость legacy-статуса `overdue`

В текущей БД `overdue` уже входит в enum статусов, поэтому утверждение «такого
статуса нет» неверно. Целевая модель запрещает создавать новые переходы в него и
считает просрочку по `due_date`.

До включения новых инвариантов миграция нормализует существующие строки:

```text
overdue + assigned_to IS NULL -> open
overdue + assigned_to IS NOT NULL -> assigned
```

Сам enum-value пока не удаляется: удаление значения PostgreSQL enum — отдельная
рискованная операция. API больше не предлагает его как допустимый новый статус,
а тест гарантирует отсутствие строк с `status = overdue` после миграции.

### 3.5 Развёртывание

Миграция — nullable expand, backfill и индексы. `NOT NULL` для `category_id`
вводится отдельной contract-миграцией после перехода всех writers. Для больших
production-таблиц индексы создаются безопасным для блокировок способом, выбранным
после оценки объёма. Обновить и Alembic, и `schema.sql`, поскольку чистое окружение
проекта поднимается через bootstrap-схему.

## 4. Правила цепочки

### 4.1 Зелёные обходы принимает reviewer

`is_green = status == completed AND issues_count == 0`.

Текущий completion flow автоматически создаёт issue на каждый defect, поэтому
для новых корректно завершённых обходов `issues_count == 0` достаточно. Для
защиты от legacy/повреждённых данных stats-запрос всё же классифицирует результат
по наличию defect-ответов; несоответствие defect↔issue логируется как data-quality
ошибка, а не превращает дефектный обход в зелёный.

- В `InspectionOut` добавить `is_green: bool`.
- `POST /inspections/bulk-accept` разрешить только reviewer; admin получает 403.
- В одиночном `PATCH /inspections/{id}` admin не может проставить review-поля
  зелёному обходу; reviewer может.
- Проверка выполняется сервером по состоянию БД, не по присланному клиентом флагу.
- Существующие права admin на незелёные кейсы не меняются.

### 4.2 Исполнитель обязателен при устранении

При переходе issue в `fixed` итоговое значение `executor_name` (старое либо
переданное в этом PUT) должно быть непустым после `strip()`, иначе 400
«Укажите исполнителя работ». Проверка находится рядом с существующим требованием
фото исправления.

`executor_name` редактируют reviewer/admin. В `IssueUpdate` и `IssueOut` добавить
его явно; patch-семантика должна использовать `model_fields_set`, чтобы
«не передано» отличалось от явного очищения. В `IssueOut` также добавить
`category_id`, `category_name` и вычисляемый `is_overdue`.

### 4.3 Просрочка вычисляется

```text
is_overdue = due_date < today_msk
             AND status in {open, assigned, in_work, revision_needed}
```

`due_date IS NULL` не просрочен. Сравнение выполняется с датой Москвы. Никакая
фоновая задача не мутирует статус. Stats считает overdue только внутри когорты
`found` выбранного периода.

## 5. Общий stats-сервис

До роутера выделить:

```text
app/services/statistics/
├── definitions.py   # DONE statuses, status buckets, percent()
├── filters.py       # период MSK и role/district scope
├── queries.py       # групповые SQLAlchemy-запросы
└── service.py       # типизированные DTO и инварианты
```

Требования:

- районные значения считаются групповыми запросами, не циклом запросов на район;
- totals суммируются из районных строк либо тем же snapshot, но не отдельной
  расходящейся формулой;
- scope reviewer применяется до агрегации;
- `generated_at/as_of`, период и timezone являются частью результата;
- Dashboard, PPTX, legacy summary и районная сводка Excel используют сервис;
- индексы добавляются только после `EXPLAIN (ANALYZE, BUFFERS)` на
  production-like объёме.

## 6. Stats API (`/api/v1/stats`)

Все эндпоинты: `require_role("reviewer", "admin")`. Reviewer с `district_id`
жёстко скоуплен на сервере; переданный чужой район игнорируется. Инспектор новый
stats API не видит — frontend не должен показывать ему вкладки, иначе UI и API
противоречат друг другу.

Общие параметры: `date_from`, `date_to` (`YYYY-MM-DD`, МСК). Валидировать
`date_from <= date_to` и ограничить максимальный интерактивный диапазон (например,
366 дней), чтобы запрос непрерывной динамики нельзя было использовать как DoS.

### 6.1 `GET /stats/dashboard`

Ответ содержит `period`, `timezone: "Europe/Moscow"`, `generated_at`,
`districts` и `totals`. `StatsDistrictRow`:

- `district_id`, `district_name`;
- `total_sites` — активные площадки сейчас;
- `sites_inspected` — distinct площадки с DONE-обходом по `completed_at`;
- `coverage_pct`;
- `inspections_total` — **DONE-обходы по `completed_at`** (название сохранено из
  утверждённого контракта; в коде описать явно, что это не все созданные записи);
- `inspections_green`, `inspections_with_defects`;
- `issues_found`, `issues_closed`, `issues_on_check`, `issues_revision`,
  `issues_in_work`, `issues_open`, `issues_not_fixed`, `issues_overdue`;
- `issues_closed_pct`.

`inspections_total = inspections_green + inspections_with_defects`. Площадки,
деактивированные сейчас, не входят в `total_sites`; их обходы также следует
исключить из числителя coverage, чтобы процент не превышал 100. Это показатель
текущего активного инвентаря за период, не исторический SLA. Исторический SLA
потребует истории активности площадок.

Районы сортируются по названию. Nil UUID totals сохраняется для совместимости.

### 6.2 `GET /stats/dynamics`

```json
{"days":[{"date":"YYYY-MM-DD","inspections":0,"issues_found":0,"closure_events":0}]}
```

- `inspections` — DONE по `completed_at`;
- `issues_found` — по `Issue.created_at`;
- `closure_events` — переходы в closed по `IssueStatusHistory.created_at`.

Backend генерирует непрерывный диапазон дней, включая нулевые. Старое имя
`issues_closed` не используется здесь, чтобы событие не спутали с текущей
когортной корзиной.

### 6.3 `GET /stats/categories`

Возвращаются все активные категории по `sort_order`, включая нулевые. Для каждой:
`category_id`, `name`, `found`, `closed`, `on_check`, `revision`, `in_work`,
`open`, `not_fixed`, `overdue`, `closed_pct`. Применяются та же когорта, buckets,
scope и `as_of`, что в dashboard.

### 6.4 `GET /stats/shtab.pptx`

Возвращает attachment `.pptx` по § 7. Параметры периода те же; при их отсутствии
используется прошлая полная неделя.

### 6.5 Legacy `/reports/weekly` и `/reports/monthly`

- Добавить опциональные `date_from/date_to` и календарные дефолты МСК вместо
  скользящих UTC-окон 7/30 дней.
- Старые response fields не удалять.
- `monthly.issues_closed` считать по переходам `IssueStatusHistory` в периоде,
  не по `Issue.updated_at`.
- Переиспользовать общий filter/scope/query layer.
- Изменение семантики закрытий зафиксировать в release notes и контрактных тестах.

## 9. Порядок реализации

Каждая фаза — отдельный PR с миграционными/контрактными тестами.

1. **Фаза 0 — characterization:** тесты текущих ролей, переходов, MSK-границ,
   created-vs-completed и legacy overdue; эталонный dataset для сверки.
2. **Фаза 1 — expand data model:** категории, nullable-поля, backfill,
   нормализация legacy overdue, `schema.sql`; старый UI продолжает работать.
3. **Фаза 2 — chain rules и writers:** dual-write категорий, `is_green`, права
   приёмки, executor gate, `is_overdue`; перевести все category consumers.
4. **Фаза 3 — statistics service/API:** grouped queries, DTO, dashboard,
   dynamics, categories и legacy fixes.
5. **Фаза 4 — PPTX и интеграция Excel:** renderer PPTX; районная сводка Excel
   переходит на общий service без обязательного редизайна workbook.
6. **Фаза 5 — frontend:** роли, tabs, statsApi, charts, PPTX preview/download.
7. **Фаза 6 — contract migration:** после production-аудита сделать category FK
   обязательным и отдельно решить удаление legacy string/enum-value.

Перед переключением dashboard включить dual-run старого и нового агрегатора на
production-like дампе, логировать расхождения по району/метрике без персональных
данных. Новый API включается после объяснения каждого расхождения.

## 10. Definition of Done

- одна реализация period/scope/buckets/percent используется всеми сводками;
- завершённые обходы относятся к периоду по `completed_at`;
- когортные closed и события закрытия названы и считаются раздельно;
- overdue вычисляется по due date, legacy status больше не создаётся;
- все category readers/writers переведены до удаления legacy-колонки;
- API, PPTX и районная сводка Excel совпадают на эталонном dataset;
- reviewer никогда не получает чужой район; inspector не видит stats API/UI;
- тесты покрывают MSK-полночь, пустой период, повторное закрытие, все статусы,
  повторные обходы, деактивированные площадки и процентные границы;
- запросы не растут по числу районов; планы и p95 зафиксированы до индексов;
- миграции имеют проверяемый upgrade/rollback и не требуют долгой блокировки;
- каждый экспорт содержит период, timezone, generated_at и версию методики `v2`.
