# Модель статистики и штабной отчётности (v2)

Документ — единый источник правды для переработки статистики, дашборда и штабных отчётов.

**Статус:** утверждено владельцем продукта 19.08.2026. Дополнено и состыковано с реальным
кодом (модели/эндпоинты/permissions) в этой ревизии — открытые вопросы автора закрыты
конкретными решениями, см. пометки «Решено:» по тексту.

## 1. Цель

Единая, непротиворечивая модель воронки нарушений и охвата обходов, из которой считаются:
дашборд в приложении (5 вкладок, §7), легаси-отчёты `/reports/weekly` и `/reports/monthly`
(чинятся, не удаляются, §5.5), Excel-выгрузка (`/reports/export.xlsx`, уже существует,
не входит в эту переработку) и новый штабной PPTX-слайд (§6). Сегодня эти источники
считают одно и то же по-разному (например, `admin_dashboard` фильтрует обходы по
`created_at`, а не по завершению) — это и есть корень регулярных «расхождений в цифрах»,
которые уже несколько раз разбирались вручную в этом проекте.

## 2. Терминология и воронка нарушений

Все метрики нарушений считаются по замечаниям (issues), СОЗДАННЫМ в отчётном периоде,
с их ТЕКУЩИМ статусом (тот же принцип «событие vs снимок», что уже применён в
`reports.py` после фикса «issue status buckets vanishing from dashboard», PR #99 —
эта модель делает его единым правилом, а не точечным патчем).

```
ВЫЯВЛЕНО (found) = issues.created_at ∈ период
├── УСТРАНЕНО (closed) = status == 'closed'  (прошло проверку админа)
└── НЕУСТРАНЕНО (not_fixed) = found − closed:
    ├── Не приступали (open) = status == 'open'
    ├── В работе (in_work) = status ∈ {assigned, in_work}
    ├── На проверке у админа (on_check) = status ∈ {fixed, control}
    ├── На доработке (revision) = status == 'revision_needed'
    └── Просрочено (overdue) = status ∈ {open, assigned, in_work, revision_needed}
                                 И due_date < сегодня (МСК)
                                 — вычисляемое пересечение, не отдельный бакет суммы
```

Проценты: всегда целые, `ROUND_HALF_UP` (`int(x*100/y + 0.5)` для `x, y ≥ 0`); деление
на 0 → 0.

Периоды: МСК-дни, полуоткрытый интервал `[date_from 00:00 МСК, date_to+1 00:00 МСК)` →
UTC-границы. **Решено:** переиспользовать существующую `app.services.timezone.msk_day_bounds_utc`
как есть — она уже делает ровно это (проверено по коду, включая явный учёт МСК-полуночи,
а не наивного UTC).

Штаб-неделя по умолчанию: прошлая полная неделя Пн–Вс (МСК). Штабы по средам.

## 3. Модель данных (миграция Alembic)

### 3.1 Новая таблица `issue_categories`

```sql
CREATE TABLE issue_categories (
    id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    name        VARCHAR(200) NOT NULL UNIQUE,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    is_active   BOOLEAN NOT NULL DEFAULT true,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Решено** (был открытый пункт «gen_random_uuid?»): проект везде использует
`uuid_generate_v4()` (расширение `uuid-ossp`, уже включено — см. `schema.sql`), не
`gen_random_uuid()` (`pgcrypto`). Используем тот же дефолт, что и у всех существующих
таблиц с UUID PK, ради единообразия.

Seed (9 категорий, `sort_order` 10..90, `Прочее` — 999):

| sort_order | name |
|---|---|
| 10 | Оборудование |
| 20 | Покрытие |
| 30 | Ограждения |
| 40 | МАФ |
| 50 | Санитарное состояние |
| 60 | Безопасность |
| 70 | Документация |
| 80 | Освещение |
| 999 | Прочее |

### 3.2 `checklist_items`

`+ category_id UUID REFERENCES issue_categories(id) NULL` (index).
Старая колонка `category` (`String(200)`, подтверждено в `models.py`) остаётся в схеме,
но deprecated — код (ORM-модель, роутеры, схемы) больше её не читает и не пишет.

### 3.3 `issues`

`+ category_id UUID REFERENCES issue_categories(id) NULL` (index)
`+ executor_name VARCHAR(300) NULL`

### 3.4 Миграция данных (внутри той же ревизии Alembic)

1. Вставить 9 категорий (идемпотентно — `ON CONFLICT (name) DO NOTHING`).
2. `checklist_items.category` (text) → `category_id`: нормализация (`lower`, `trim`),
   маппинг по вхождению ключевых слов, в порядке приоритета (первое совпадение
   побеждает — важно для пунктов, где встречается несколько ключевых слов сразу,
   например «фото при уборке мусора» → должно уйти в Санитарное, а не в Прочее):
   - `'покрытие'` → Покрытие
   - `'оборудован'`, `'качел'`, `'горк'`, `'турник'`, `'карусел'`, `'тренаж'`, `'песочниц'` → Оборудование
   - `'огражден'` → Ограждения
   - `'маф'`, `'скамей'`, `'урн'` → МАФ
   - `'санитар'`, `'мусор'`, `'уборк'`, `'чистот'` → Санитарное состояние
   - `'безопасн'` → Безопасность
   - `'документ'`, `'табличк'`, `'паспорт'`, `'вывеск'` → Документация
   - `'освещен'`, `'свет'` → Освещение
   - прочее/NULL → Прочее
3. `issues.category_id`: из связанного `checklist_answer → checklist_item.category_id`
   (уже посчитанного в шаге 2); если `checklist_answer_id IS NULL` (замечание заведено
   вручную, не по пункту чек-листа — см. комментарий у поля в `models.py`) — по тем же
   ключевым словам, но по `issues.title`; иначе Прочее.

Обе миграции данных пишутся как raw SQL внутри `upgrade()` (тот же подход, что уже
используется в ревизии `49e5a376fe4f_initial_schema_mirrors_schema_sql.py` — прямое
исполнение SQL для контролируемого поведения на реальных данных, без ORM bulk-update).

### 3.5 Пересчёт

Денормализованных таблиц статистики нет — всё считается на лету из `issues`/`inspections`,
поэтому после миграции статистика автоматически «пересчитана». На проде: `alembic upgrade
head` + smoke-проверка `/api/v1/stats/dashboard` (после того как роутер появится, §5).

## 4. Правила цепочки (изменения поведения)

### 4.1 Зелёные обходы — только проверяющие

«Зелёный» = `status == 'completed'` И нет дефект-ответов И нет замечаний.

**Решено** (было два открытых вопроса — упрощение и обработка `bulk-accept`):

- Упрощение определения: в текущем коде (`update_inspection`, `inspections.py`) КАЖДЫЙ
  чек-лист-ответ со статусом `defect` **автоматически** создаёт `Issue` при завершении
  обхода (нет ручного шага, который мог бы это пропустить — см. комментарий в коде
  «Автосоздание замечания по каждому пункту»). Значит «нет дефект-ответов» и «нет
  замечаний» — не два независимых условия, а одно: `is_green = status == 'completed'
  AND issues_count == 0`. Это и есть промежуточное поле `issues_count` в `InspectionOut`,
  оно уже есть в схеме.
- `POST /inspections/bulk-accept` **уже существует** (не новый эндпоинт, как читалось
  в черновике — он реализован и по своему запросу-кандидату (`completed`,
  `reviewed_by IS NULL`, `issues_count == 0`) и так обрабатывает **исключительно**
  зелёные обходы; «незелёных» там в принципе не бывает). Значит вариант «admin →
  обрабатывать только незелёные» структурно не имеет смысла для этого эндпоинта — это
  был бы уже другой инструмент. Решение: `bulk-accept` становится **эндпоинтом только
  для reviewer** (`current_user.role != "reviewer"` → 403 «Массовая приёмка — только
  для проверяющего»). Админ телом занимается финальными решениями по незелёным
  замечаниям (`closed`/`revision_needed`), а не штамповкой чистых обходов — это и
  создаёт нужное разделение труда.
- Тот же запрет — для **одиночной** приёмки: в `PATCH /inspections/{id}`, когда
  `current_user.role == 'admin'` и обход зелёный (`is_green` на объекте ДО применения
  `data.status`), выставление `reviewed_by`/`reviewed_at` для админа блокируется 403
  («Зелёные обходы принимает проверяющий»). Незелёные обходы админ по-прежнему может
  проверять как раньше (правка не трогает остальную логику `update_inspection`).

В списке обходов (`GET /inspections/`, тот же `InspectionOut` — отдельной
`InspectionListItem` в кодовой базе нет) добавить вычисляемое поле `is_green: bool`
по формуле выше.

### 4.2 Исполнитель обязателен для устранения

`PUT /issues/{id}` со `status='fixed'`: если `executor_name` пуст (и не передан в
этом же запросе через `IssueUpdate.executor_name`) → 400 «Укажите исполнителя работ».
Проверяется в той же ветке `if data.status == "fixed":`, что и существующая проверка
фото исправления (`Photo.target_type == "issue_fix"`) — оба гейта защищают один и тот
же переход, логично держать их рядом.

`executor_name` редактируется reviewer/admin через тот же `PUT` (добавить поле в
`IssueUpdate`, `model_fields_set`-паттерн не нужен — это просто строка, не nullable-FK,
как `assigned_to`).

В `IssueOut` добавить: `executor_name`, `category_id` (+ `category_name` — join,
как уже сделано для `district_name`/`site_name` в `_issue_to_out`), `is_overdue`.

### 4.3 Просрочка — вычисляемая

Никаких статус-мутаций (в БД по-прежнему нет статуса `overdue`, использовать который
для «просрочено» и предлагал старый код — сейчас это /вычисляемое/ пересечение, а не
реальный статус, который нужно было бы кем-то проставлять фоновой задачей).

`is_overdue = due_date < today_msk AND status ∈ {open, assigned, in_work, revision_needed}`.

В `stats`-метриках: `overdue = count(...)` по found-в-периоде с этим условием.

## 5. Stats API (новый роутер `app/routers/stats.py`, prefix `/api/v1/stats`)

Все эндпоинты: `require_role("reviewer", "admin")` (готовая зависимость из
`app.services.permissions`); reviewer с `district_id` — жёстко скоуплен (игнорировать
чужой `district_id` в параметрах запроса — тот же паттерн, что уже применён в
`reports.py`: `if current_user.role == "reviewer" and current_user.district_id is not
None: district_id = str(current_user.district_id)`).

Общие параметры: `date_from`, `date_to` (`YYYY-MM-DD`, МСК). По умолчанию: текущая
неделя (Пн 00:00 – сегодня 23:59 МСК) — тот же дефолт, что фронтенд уже показывает
на `/dashboard` (см. `DashboardPage.tsx`, изменено в этой же сессии).

### 5.1 `GET /stats/dashboard` → `StatsDashboardOut`

```json
{
  "period": {"date_from": "...", "date_to": "..."},
  "districts": [StatsDistrictRow, ...],
  "totals": StatsDistrictRow
}
```

`StatsDistrictRow`:
- `district_id` (uuid str; у `totals` — `"00000000-0000-0000-0000-000000000000"`, `name` `"ВСЕГО"` — тот же паттерн nil-UUID, что уже используется в `admin_dashboard`)
- `district_name`
- `total_sites: int` (активные площадки района)
- `sites_inspected: int` (DISTINCT площадки с обходом в DONE-статусе в периоде)
- `coverage_pct: int`
- `inspections_total: int`

**Решено** (было явно помечено как открытое автором): обходы считаются по
`completed_at`, а не по `created_at`. Это осознанное ломающее изменение относительно
старого `admin_dashboard` (который весь этот проект уже несколько раз чинили за
путаницу между «когда начали» и «когда закрыли», см. PR #99) — фиксируется здесь как
единственное определение на будущее, старое поведение `reports.py` не трогается (он
остаётся для Excel-выгрузки, отдельный источник, не путать эндпоинты).

- `inspections_green: int` (DONE по `completed_at` в периоде, 0 дефектов)
- `inspections_with_defects: int` (≥1 дефект)
- `issues_found, issues_closed, issues_on_check, issues_revision, issues_in_work, issues_open, issues_not_fixed, issues_overdue: int` (воронка, §2)
- `issues_closed_pct: int`

Сортировка `districts`: по названию (алфавит).

### 5.2 `GET /stats/dynamics`

```json
{ "days": [ {"date": "YYYY-MM-DD (МСК)", "inspections": N, "issues_found": N, "issues_closed": N} ] }
```

`inspections` — DONE по `completed_at`; `issues_found` — по `created_at`; `issues_closed`
— по `IssueStatusHistory.new_status == 'closed'` И `created_at` в этот день (тот же
запрос, что уже добавлен в `export_xlsx` для «Топ районов по устранению замечаний» —
переиспользуем тот принцип «закрытие — событие, не снимок»).

Дни без данных — тоже присутствуют с нулями (непрерывная ось для графиков): диапазон
дат генерируется на бэкенде (`date_from`..`date_to` построчно), а не собирается из
факта наличия строк в БД, как сейчас в `reports.py`'s «Динамика» (там дни без единого
обхода просто отсутствуют — для непрерывного графика recharts на фронтенде это ломает
ось X).

### 5.3 `GET /stats/categories`

```json
{ "categories": [ {"category_id": "...", "name": "...", "found": N, "closed": N, "on_check": N, "revision": N, "in_work": N, "open": N, "not_fixed": N, "overdue": N, "closed_pct": N} ] }
```

Только активные категории (`is_active = true`), сортировка по `sort_order`; категории
с нулями тоже включать (постоянный список для сравнимых графиков между периодами).

### 5.4 `GET /stats/shtab.pptx?date_from&date_to`

`FileResponse` (`.pptx`) — см. §6.

### 5.5 Починка legacy `/reports/weekly` / `/reports/monthly`

Добавить опциональные `date_from`/`date_to` (МСК, дефолт — текущая неделя/месяц МСК
вместо скользящих UTC-окон `datetime.now(timezone.utc) - timedelta(days=7/30)`, которые
сейчас там жёстко зашиты — та же категория бага, что уже чинили в остальном `reports.py`).

`issues_closed` в `monthly` считать по `IssueStatusHistory` (`new_status='closed'`,
`created_at ∈ период`) — как в `export.xlsx`, а не по текущему
`Issue.status == 'closed' AND updated_at >= month_ago` (последнее считает по
`updated_at`, который трогается ЛЮБЫМ изменением замечания, не только закрытием —
отдельный, самостоятельный баг, найденный при сверке этой ревизии с кодом, но не
входящий в объём переработки статистики — фиксируется отдельным issue/PR, не здесь).

Старые поля ответа не ломать (`ReportWeeklyOut`/`ReportMonthlyOut` остаются как есть).

## 6. Штаб-слайд PPTX (`python-pptx`; добавить в `requirements.txt`)

Слайд 16:9 (13.333″ × 7.5″), шрифт везде «Century Gothic» (тот же, что уже используется
во всех существующих штабных презентациях — см. слайд 26 текущей колоды, разобранной в
этой сессии).

Верхняя полоса: слева текст «УПРАВЛЕНИЕ ЖИЛИЩНО-КОММУНАЛЬНОГО ХОЗЯЙСТВА» (маленький,
серый), справа заголовок «Обходы детских и спортивных площадок САО — итоги недели»
(жирный). Акцентный бордовый `#9E2B25`.

Таблица (по данным `/stats/dashboard` за период; дефолт — прошлая неделя Пн–Вс):

Колонки: `№ | Район | Площадок | Обойдено | % охвата | Выявлено | Устранено | На доработке | Не устранено | % устранения`

**Решено** (снят открытый вопрос про «Неизвестный район»): по схеме БД
`sites.courtyard_id`, `courtyards.district_id` — оба `NOT NULL FK`. Площадка без района
физически невозможна на уровне схемы (проверено в `models.py`) — сценарий «показать
отдельной строкой, если есть данные» неприменим, убран из дизайна. Всегда ровно 16
районов округа.

Сортировка: `% устранения ↓`, затем `% охвата ↓`.

ИТОГО-строка (`totals` из `/stats/dashboard`).

Цвет `%`-ячеек: `100` → `#63BE7B`; `70–99` → `#FFD966`; `50–69` → `#F4B183`; `<50` →
`#E06666`; текст тёмный. Шапка `#595959`, белый текст. ИТОГО `#D9D9D9`, жирный.

Под таблицей — автотекст: «За период с {дд.мм.гггг} по {дд.мм.гггг} инспекторами САО
обойдено {inspected} из {total} площадок ({coverage}%). Выявлено нарушений: {found},
из них устранено и принято {closed} ({closed_pct}%), на доработке {revision}, работы
не начаты или в работе {open+in_work}.»

Слайд 2: «Нарушения по категориям» — таблица категорий (`found`/`closed`/`%` устранения
с той же раскраской) + самая проблемная категория текстом (наибольший `not_fixed`).

Файл: `shtab_YYYY-MM-DD_YYYY-MM-DD.pptx`.

Тесты: файл открывается `python-pptx`, размер 16:9, кол-во строк таблицы = районы+2
(шапка + ИТОГО), пороги цвета (параметризованный тест на границы 49/50/69/70/99/100%).

## 7. Frontend (подробное ТЗ для дизайн-лейна)

### 7.2 Дашборд — 5 вкладок (tabs)

Маршруты `/dashboard` и `/admin/dashboard` (сохранить dual-mount — тот же паттерн, что
уже есть в `DashboardPage.tsx`/`IssuesPage.tsx`). Дефолтный период: текущая неделя

(типы обновить в `src/types/index.ts`, api-клиент — в `src/lib/api.ts`, рядом с
существующим `reportsApi`, как `statsApi`).

**Вкладка 1 — Обзор:**
KPI-карточки (Площадок / Обойдено (% охвата) / Обходов / Зелёных / С нарушениями /
Выявлено нарушений / Устранено (%) / На доработке) + воронка нарушений (горизонтальные
бары `recharts`, тот же паттерн визуализации, что уже используется в проекте) +
охват-донат (проверено/не проверено, палитра status-цветов — та же пара, что уже
устоялась в Excel-экспорте: зелёный/серый).

**Вкладка 2 — Динамика:**
Линейный график `/stats/dynamics` (обходы/выявлено/устранено — 3 линии, непрерывная
ось дат) + под графиком — таблица по дням (та же мини-таблица, что уже есть в листе
«Динамика» Excel-экспорта, но с 3 колонками вместо 1).

**Вкладка 3 — Категории:**
`/stats/categories` — горизонтальный bar chart по `found`, отсортированный по убыванию
+ таблица категорий с `%` устранения (та же цветовая шкала 50/70/100, что в PPTX §6, —
единая палитра между экспортом и приложением, а не разные пороги в разных местах).

**Вкладка 4 — По районам:**
Полная таблица `StatsDistrictRow` (все колонки из §5.1), с сортировкой по клику на
заголовок столбца, цветовая шкала `%` — та же (§6). Клик по строке района — фильтрует
все остальные вкладки по этому `district_id` (переиспользует уже существующий
`districtFilter` в `DashboardPage.tsx`).

**Вкладка 5 — Штаб-отчёт:**
Выбор периода (дефолт — прошлая полная неделя Пн–Вс МСК, отдельно от общего периода
дашборда сверху — штабной слайд должен быть воспроизводим независимо от того, какой
период открыт на других вкладках) + кнопка «Скачать PPTX» (`GET /stats/shtab.pptx`) +
превью первого слайда таблицы (тот же компонент таблицы, что и вкладка 4, просто
отфильтрованный под выбранный штабной период — не отдельная реализация).

## 8. Порядок реализации (фазы)

Проект большой — реализуется поэтапно, каждая фаза — отдельный PR с тестами, как и
весь остальной код в этом репозитории (см. историю PR #96–103).

1. **Фаза 1 — модель данных.** Alembic-миграция §3 (таблица `issue_categories`,
   колонки `category_id`/`executor_name`, миграция существующих данных). Ничего не
   ломает — только nullable-добавления и новая независимая таблица; существующий код
   работает без изменений до тех пор, пока новые поля не начнут читаться.
2. **Фаза 2 — правила цепочки.** §4: `is_green`, ограничение `bulk-accept` и
   одиночной приёмки для admin, обязательный `executor_name` при `fixed`,
   `is_overdue` на `IssueOut`.
3. **Фаза 3 — Stats API.** Роутер `app/routers/stats.py` целиком (§5.1–5.4) + починка
   `/reports/weekly`/`/reports/monthly` (§5.5).
4. **Фаза 4 — PPTX-генератор.** §6, по образцу уже готового `export_xlsx` (стиль/шрифты/
   цвета переиспользуются оттуда, где возможно).
5. **Фаза 5 — фронтенд.** §7: шрифт, 5 вкладок, `statsApi`, дизайн деталей из §7.3.

Начинаем с Фазы 1 — она нужна всем остальным фазам и безопасна сама по себе.
